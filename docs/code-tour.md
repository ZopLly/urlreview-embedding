# Как читать URL Review целиком

Это путеводитель по исходникам для самостоятельного изучения. Начните с общей схемы, затем откройте файлы по ссылкам. В C, Python, shell, Makefile и конфигурации добавлены русские комментарии «Пояснение» перед каждой непустой строкой кода. Один комментарий может занимать несколько строк. Если на одной исходной строке несколько команд, пояснение описывает их последовательность. Пустые строки только разделяют части текста; исходные комментарии и документационные строки уже являются пояснениями.

Построчные комментарии объясняют существующую реализацию. Они не добавляют автоматическую разметку и не меняют алгоритмы. Сторонние библиотеки, виртуальное окружение и веса модели не комментируются: их роль описана здесь, а собственный код интеграции — в исходниках.

## Что делает программа

Человек читает описание сайта, сравнивает его с исходным классом и выбирает решение. Программа помогает просматривать длинные описания, выбирать существующие категории и сохранять работу в отдельный CSV.

- **domain** — адрес сайта.
- **class** — исходная категория, которую проверяет человек.
- **label** — дополнительные или исправленные категории, точные английские коды через запятую.
- **action** — пусто до проверки; затем OK, ERROR или NOT_DESC.
- **description** — исходный текст описания сайта.

OK подтверждает class; label добавляет категории. ERROR не подтверждает class; label содержит исправленные категории. NOT_DESC отмечает недостаточное описание и может иметь пустой label по принятому в проекте правилу.

Эмбеддинги помогают найти похожие уже проверенные сайты. Они не назначают action или label и не переобучаются от каждого решения.

## Две программы и связь между ними

Основное приложение написано на C и работает в терминале через ncursesw. Необязательный Python-компонент рассчитывает векторы описаний готовой локальной моделью ONNX. Между ними нет постоянно работающего Python-сервера: связь — бинарный файл .uremb.

~~~mermaid
flowchart TD
    CLI["main.c: аргументы запуска"] --> CSV["csv.c: байты → UTF-8 → Table"]
    CLI --> GUIDE["guide.c: categories.tsv → Guide"]
    CSV --> STORE["store.c: отдельная рабочая копия и блокировка"]
    STORE --> UI["ui.c: просмотр → категории → подтверждение"]
    GUIDE --> UI
    UI --> COMMIT["store_commit: action/label → CSV → временный файл → rename"]
    COMMIT --> STORE
    UI --> BROWSER["browser.c: HTTP(S) → xdg-open"]
    SOURCE["Исходный CSV"] --> PY["local_embeddings.py: токены → ONNX → векторы"]
    PY --> INDEX["Файл .uremb"]
    INDEX --> SEARCH["embedding.c: проверка индекса и косинусный поиск"]
    STORE --> SEARCH
    SEARCH --> UI
~~~

При первом чтении можно идти по текстовым цепочкам:

1. Запуск: main → guide_read → store_open → embedding_read, если индекс указан → ui_run.
2. Сохранение: choose_categories → selected_label → confirm → store_commit → table_serialize → convert_text → atomic_write.
3. Поиск: клавиша P → similar → embedding_search → similar_detail.
4. Построение индекса: Python main → Encoder → build_index → Encoder.__call__ для каждого непустого описания.

Реализации функций находятся в .c; заголовки .h объявляют, какие типы и функции доступны другим файлам. В Python определения и реализация находятся в одном .py.

- .venv-embeddings/ — установленный Python и сторонние библиотеки; это не собственные исходники.
- build/ — скомпилированные тесты и вспомогательные бинарники.
- url-review — готовый бинарник, собираемый из src, а не файл исходного кода.

- *.uremb — числовой индекс конкретных доменов и описаний.

## Как представлены таблицы в C

Row — одна логическая CSV-запись. Она хранит char **cells: массив адресов строк. Каждая строка заканчивается нулевым байтом. count — число ячеек, а не число символов.

Table хранит массив Row. Нулевая запись — заголовок, поэтому t.count - 1 даёт число сайтов. Заголовки могут идти в любом порядке: col[DESCRIPTION] содержит реальную позицию description, найденную при проверке схемы. Вызов cell(t, row, DESCRIPTION) скрывает это отображение.

Store владеет Table, путями, именем кодировки и snapshot. Снимок — точные байты последней принятой рабочей копии. Он нужен, чтобы заметить внешнее редактирование. lock_fd удерживает межпроцессную flock на протяжении сеанса.

Guide хранит массив Category. UI заимствует указатели на Store, Guide и Embedding, но отдельно владеет историей, отложенными флагами и экранными строками. main освобождает общие компоненты после ui_run.

Embedding хранит один плоский массив float. Вектор строки r начинается с vectors + r * 384. В памяти место строки 0 зарезервировано под заголовок, а в файле индекса заголовок CSV отдельного вектора не имеет.

Пример владения: read_bytes возвращает выделенный блок, поэтому вызывающий код делает free. cell возвращает адрес строки внутри Table: отдельно освобождать его как независимую копию нельзя. str_copy делает новую строку, принадлежащую вызывающему коду.

В store_commit адреса a и l указывают именно на указатели ячеек. Поэтому *a = str_copy(action) заменяет адрес action в таблице. Старые строки временно сохраняются для отката.

## Почему CSV-парсер имеет четыре состояния

Простое деление строки по ';' сломало бы описание «товары; доставка». Поэтому table_parse последовательно читает байты и помнит состояние:

| Состояние | Что сейчас читаем | Особое правило |
|---|---|---|
| START | Начало поля | Кавычка может открыть quoted-поле |
| PLAIN | Обычное поле | Разделитель и перевод строки завершают поле/запись |
| QUOTED | Внутри кавычек | Разделитель и переводы строк являются данными |
| CLOSED | Встретили закрывающую кавычку | Ещё одна кавычка означает кавычку внутри данных |

finish_field передаёт накопленный текст Row, finish_row передаёт Row таблице. Это передача владения указателями, а не повторное копирование всех символов.

После разбора schema проверяет уникальные обязательные заголовки, одинаковую ширину записей и action. При записи table_serialize экранирует нужные поля и удваивает кавычки. Оформление CSV может нормализоваться, но значения ячеек должны остаться теми же.

## Что именно происходит при сохранении

1. UI держит выбранные категории в отдельном массиве selected.
2. selected_label собирает английские коды в строку label.
3. confirm показывает действие и label; одного выбора категории для записи недостаточно.
4. store_commit сохраняет старые указатели action/label и временно ставит новые.
5. table_serialize собирает всю таблицу, convert_text возвращает кодировку рабочего файла.
6. atomic_write сверяет рабочую копию со snapshot, пишет временный файл рядом и вызывает fsync файла.
7. Перед rename ещё раз проверяется отсутствие внешних изменений.
8. rename заменяет рабочую копию; затем обновляется snapshot и вызывается fsync каталога.

| Результат | Файл | Память и интерфейс |
|---|---|---|
| SAVE_FAILED=0 | Новая версия не была принята этой операцией | Старые action/label восстанавливаются; перехода дальше нет |
| SAVE_OK=1 | Замена и синхронизация подтверждены | Новые значения остаются; UI переходит дальше |
| SAVE_UNCERTAIN=2 | Замена уже произошла, fsync каталога отказал | Новые значения остаются; UI предупреждает и ждёт повторной попытки |

Это объясняет, почему логическая проверка «любой ненулевой результат равен обычному успеху» для интерфейса была бы неверной: 2 тоже ненулевой, но автоматический переход допустим только при SAVE_OK.

flock предотвращает второй сеанс самого приложения, а snapshot обнаруживает внешние изменения, заметные при сравнениях. Эти механизмы не заставляют сторонние офисные редакторы соблюдать блокировку и не дают универсальной гарантии от всех возможных гонок или аппаратных сбоев.

## Как читать интерфейс

ncurses хранит экранный буфер; refresh применяет подготовленный кадр. LINES и COLS — размеры терминала. Координаты идут как y,x: строка, затем колонка.

UTF-8 хранится байтами, но один символ может занимать несколько байтов и несколько экранных колонок. wide_text декодирует символы в wchar_t, wcwidth измеряет их ширину, lines_make делает переносы, draw_lines рисует видимую часть.

ui_run — цикл: проверить процессы браузера → отрисовать → прочитать событие → выполнить команду → повторить. read_key превращает колесо в стрелки. timeout позволяет регулярно проверять флаг сигнала, даже если пользователь ничего не нажимает.

choose_categories, confirm, similar и viewer — вложенные циклы отдельных экранов. Они возвращаются в основной цикл, сохраняя сеанс. Коды 0/1/2 у выбора и подтверждения означают «назад/сохранено/выйти»; это отдельный контракт, не enum SaveResult.

## Эмбеддинги по шагам

Эмбеддинг — список из 384 чисел, вычисленный готовой моделью для текста. Близость направлений этих списков используется как мера смыслового сходства.

1. verify_model проверяет SHA-256 локальных ONNX и tokenizer.json.
2. Tokenizer превращает весь нормализованный по пробелам текст в идентификаторы токенов. Токен не обязательно равен слову.
3. chunks делит длинный список на окна по 320 токенов с перекрытием 32: шаг равен 288. Хвост сохраняется.
4. К каждому окну добавляются начало последовательности, токены префикса query: и конец.
5. ONNX Runtime на CPU выдаёт hidden с формой [1, количество токенов, 384].
6. Среднее по токенам окна даёт один вектор. Здесь padding выключен, а в attention_mask стоят единицы для всех переданных токенов.
7. Каждый вектор окна нормализуется, затем такие векторы складываются с одинаковым весом.
8. Сумма ещё раз нормализуется, превращается в Python list и записывается в индекс как float32.
9. C читает индекс, проверяет длины/хеши/числа и считает косинус для подходящих кандидатов.

Норма v — sqrt(sum(v[i]²)). Нормализация делит координаты на длину. Косинус q·v / (||q|| × ||v||) сравнивает направления; для единичных векторов это скалярное произведение. Значение не является вероятностью правильной категории.

Список кандидатов каждый раз берётся из текущей Table: новый action сразу включает сайт в поиск, без переобучения и пересчёта его описания. Изменённые домен или описание делают индекс устаревшим и требуют перестроения.

### Бинарный формат .uremb

| Положение | Данные | Размер |
|---|---|---|
| 0 | Сигнатура UREMB01 и LF | 8 байтов |
| 8 | Количество сайтов, uint32 little-endian | 4 байта |
| 12 | Размерность, uint32 little-endian | 4 байта |
| 16 и далее | Для каждого сайта: FNV-1a отпечаток, затем 384 float32 | 8 + 1536 = 1544 байта |

Итого размер файла равен 16 + количество_сайтов × 1544. Little-endian означает, что младший байт числа идёт первым. struct.pack('<II', ...) и little32 в C реализуют одну договорённость.

FNV-1a считается по domain + нулевой байт + description. Это проверка соответствия записи индексу, не криптографическая подпись. Отдельный SHA-256 в verify_model проверяет файлы модели; эти два хеша служат разным целям.

## Как читать тесты и сборку

В Makefile строка «цель: зависимости» говорит, когда пересобирать результат. Следующая строка с табуляцией — команда shell. -I задаёт поиск заголовков, -l подключает библиотеку, -o задаёт имя результата. .h содержит объявления для компилятора; линкер связывает вызовы с реализациями в .c и библиотеках.

PTY — псевдотерминал: приложение видит терминал, а тест посылает клавиши и читает экранные байты. --wrap=fsync и --wrap=fopen подменяют вызовы только в специальных тестовых бинарниках. Подмена Encoder возвращает известные числа и позволяет проверить формат без загрузки нейросети. smoke, в отличие от таких тестов, запускает настоящую установленную модель на трёх вымышленных текстах.

## Порядок самостоятельного чтения

1. Пройдите [README](../README.md) и эту карту.
2. Прочитайте core.h, затем main.c: типы и общий маршрут.
3. Проследите cell, table_read, schema и table_parse в csv.c.
4. Проследите store_commit → atomic_write в store.c.
5. В ui.c начните с ui_run и render, затем choose_categories и confirm; Unicode-помощники можно разбирать вторым проходом.
6. Откройте test_core.c и test_ui.py: тесты показывают конкретные вызовы и действия пользователя.
7. Для эмбеддингов начните с Python build_index, затем Encoder.__call__, потом C embedding_read и embedding_search.
8. Разберите Makefile и shell-обёртки, чтобы понять, как отдельные файлы превращаются в запускаемый инструмент.

[Небольшие упражнения](learning.md), [настройка эмбеддингов](embeddings.md), [сохранение и проверки](verification.md) дополняют этот маршрут. Читайте по одному пути данных и сопоставляйте комментарий с выражением под ним: это поможет со временем обходиться без подсказки.

## Расширение XLSX от 31 октября 2026

`src/workbook.c` запускает `scripts/xlsx_io.py` через отдельный Python-процесс без shell. Обмен идёт через временные дескрипторы: на чтении ZIP превращается в значения Table через внутренний CSV. На записи передаются последний снимок XLSX и маленький бинарный запрос с координатами, маской изменений и новыми action/label одной записи. Передавать и читать все описания повторно не требуется. Пользователь работает XLSX → XLSX. Подробности и замеры — в [описании сохранения](saving-performance.md).

`Table.sheet` хранит выбранное имя листа, `Table.source_rows` — настоящие номера строк Excel. `Store.xlsx` выбирает способ сериализации, а прежний `atomic_write` одинаково сохраняет CSV-байты и ZIP-байты.

Python читает связи OOXML, sharedStrings, inline strings и сохранённые результаты формул. Expat находит точные байтовые границы настоящих ячеек, отличая их от комментариев и чужих пространств имён. Меняются только отличающиеся action/label; другие байты листа и части книги сохраняются. Перед возвратом результат читается заново и сравнивается с ожидаемыми значениями. Общие/массивные формулы в редактируемом диапазоне блокируют замену.

`tests/test_xlsx.py` проверяет разреженные строки, комментарии XML, формулы, стили, сохранность частей ZIP, продолжение UI-сеанса и внешнее редактирование. `scripts/check-similarity.py` отдельно проверяет настоящую установленную модель на небольшом вымышленном наборе. Поиск теперь исключает NOT_DESC и ERROR без установленной категории.
