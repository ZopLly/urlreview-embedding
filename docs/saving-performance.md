# Ускорение сохранения XLSX

Текущий путь полного сохранения одной записи занимает около **0.5 с** на временной копии рабочей книги с 5037 записями. Подтверждённое решение по-прежнему записывается сразу в XLSX с fsync и атомарной заменой. Для использования обновлённого C-протокола перезапустите приложение; команда запуска и рабочий файл прежние.

## Передача только изменённых ячеек

При открытии Store полностью читает и проверяет книгу, запоминает схему, имя листа, физические номера строк и исходные ZIP-байты. При каждом решении C теперь передаёт Python снимок XLSX и небольшой бинарный запрос: строку Excel, столбцы action/label, длины строк, маску изменённых значений и сами значения UTF-8. Всю Table с описаниями больше не нужно сериализовать в CSV, передавать и разбирать заново.

`patch_decision` использует только координаты уже проверенной Table. Общая функция `_replace_cells` находит настоящие XML-ячейки и проверяет связанные формулы перед изменением. Неизменённое значение, в том числе формула label с сохранённым результатом, не переписывается. После сборки ZIP backend извлекает изменённый лист с проверкой CRC, разбирает XML и сравнивает записанные значения в изменённых ячейках. Неизменяемые части сохраняются исходными ZIP-блоками, поэтому повторное чтение большой sharedStrings и всех описаний не требуется. Прежний полный API `patch_workbook` с проверкой всей таблицы остаётся для полных запросов.

Маска изменений вычисляется Store по прежним значениям, а не вводится пользователем. Внутренний протокол не предназначен для применения произвольных координат к новой, ещё не проверенной книге. Защита Store от внешнего изменения, откат при неудаче до rename и статус неопределённого fsync после rename сохранены.

Полное `store_commit` на одном снимке книги:

| Вариант | Три последовательных сохранения |
|---|---|
| Исходный, повторно сжимающий всю книгу | 5.633 / 5.561 / 5.593 с |
| Только ускорение ZIP, полный обмен таблицей | 2.584 / 2.343 / 2.295 с |
| Точечный протокол решения | 0.474 / 0.508 / 0.494 с |

Отдельный замер настоящего ncurses-интерфейса в PTY от Enter подтверждения до вывода следующего экрана дал **0.503 с**. После выхода сохранённая временная копия успешно прочитана полным backend. Пользовательские исходник и рабочая книга при всех замерах не изменялись. На другом диске и компьютере время может отличаться.

## Первая оптимизация: упаковка ZIP

Причина задержки найдена профилированием снимка рабочей книги с 5037 записями. До изменения подготовка одного сохранения занимала 4.89–4.94 с. Примерно 3.11 с уходило в zlib.compress: при изменении двух маленьких ячеек повторно сжималась вся книга, включая неизменяемый sharedStrings.xml размером около 31.36 МиБ.

`scripts/zip_update.py` теперь переносит неизменённые локальные ZIP-блоки вместе с их сжатыми данными. Только изменённый XML-лист сжимается заново. Затем обновляются смещения записей центрального каталога и его завершающая запись. Формат проверен по [PKWARE APPNOTE, разделы 4.3.12 и 4.3.16](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT). Для необычных контейнеров и ZIP64-каталога сохраняется прежний совместимый путь через стандартный zipfile.

На одном и том же снимке, при одинаковом изменении одной записи:

| Версия | Подготовка XLSX к сохранению |
|---|---|
| До исправления | 4.939 с |
| После, запуск 1 | 1.591 с |
| После, запуск 2 | 1.639 с |
| После, запуск 3 | 1.715 с |

Это примерно трёхкратное ускорение подготовки книги. Время в таблице измерено на этом компьютере внутри patch_workbook, без дисковых fsync и отрисовки UI. Отдельный замер полного store_commit, включая запуск Python, проверки и запись на диск, дал 2.625, 2.267 и 2.270 с на временной копии той же книги. Отрисовка UI в этот замер не входит.

В полном API проверка входных значений и повторное чтение всей таблицы сохраняются; точечный протокол выше проверяет изменённый лист и значения ячеек. Неизменённые части ZIP копируются без повторной распаковки и проверки их CRC; существующее повреждение неиспользуемой части таким сохранением не выявляется. Замеры не меняли исходную или рабочую книгу: результаты строились в памяти или во временной директории.

Регрессионная проверка сравнивает сами сжатые данные неизменённых частей, а не только их распакованный текст. Также проверяются data descriptors потокового ZIP, повторные замены с изменением длины листа, комментарии архива, смещения и совместимый путь для ZIP с префиксом. Ускорение работает и для уже существующих рабочих XLSX: преобразование книги и перестроение эмбеддингов не нужны.
